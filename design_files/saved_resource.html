Hostel One

A two-sided PG / hostel accommodation platform. One backend service runs the property owner's side of the business, a second runs the tenant's side, and a single React app serves both — talking to each service independently, over the same shared database.

A-01

System Architecture

The web app never talks to a database directly. It holds two completely independent Axios clients — one per backend — each with its own bearer token, its own localStorage session, and its own 401→refresh interceptor. Both backends read and write the same Postgres database, but only one of them owns the schema.

Shared-database, split-ownership pattern. lessor-service and renter-service are separate Maven modules with their own copies of the JPA entities — there is no shared library between them. lessor-service runs the Flyway migrations (spring.flyway.enabled=true); renter-service has Flyway disabled entirely and simply maps onto whatever schema lessor-service has already created, so lessor-service must be migrated first in a fresh environment.

A-08

Auth & Security

Two logins, one signing key, no server-side HTTP sessions.

Token lifecycle

  • Login / registerreturns access + opaque refresh token
  • Access tokenJWT, HS256, 30 min TTL
  • Refresh tokenopaque UUID pair, 14 day TTL, stored server-side
  • Client storagelocalStorage, keyed per app
  • renter keyhostelone_renter_session
  • lessor keyhostelone_lessor_session
  • On 401single in-flight refresh, then retries the original call

What's on the token

  • subuser id
  • emailclaim
  • roleLESSOR / RENTER
  • tenanttenantId claim
  • PasswordsBCrypt
  • SessionsSTATELESS — no HttpSession
  • Method security@EnableMethodSecurity
Both services sign and verify with the same JWT secret — a deliberate choice recorded directly in JwtService's own code comment, so that a future gateway (or either service) can validate a token issued by the other without calling back to it. In practice each service still only exposes the routes and data for its own role.
Field-level encryption: an AttributeConverter (EncryptedStringConverter) applies AES-256-GCM with a random 12-byte IV per value to non-searchable sensitive columns — exact street address, payment transaction references. Searchable fields (city/state, phone/email used for login) stay plaintext at the application layer by design, relying on transport and at-rest disk encryption instead.
Audit trail: service methods annotated @Auditable(action, entityType) are wrapped by an AspectJ @Around advice that writes an AuditLog row after the method returns — actor id from the security context, entity id read reflectively off the return value.
CORS: restricted to app.cors.allowed-origins, defaulting to http://localhost:5173 — i.e. only the Vite dev server by default.
